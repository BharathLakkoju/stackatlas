## Why this matters

Teams spawn twelve threads to crunch numbers and see no speedup. Others avoid threads entirely and block the whole service on HTTP. The GIL explains **when** threads help (waiting on I/O) and **when** you need `multiprocessing`, native extensions, or `asyncio` for concurrency.

It also frames interview answers about Python vs Go/Java for CPU-heavy workloads.

## Mental model

The **Global Interpreter Lock** is a mutex in CPython protecting interpreter state. One thread runs Python bytecode in a process at a time (with brief releases around I/O and some C calls).

**CPU-bound** Python threads alternate on one core—little parallel speedup for pure Python math.

**I/O-bound** threads release the GIL while waiting on sockets, disk, or sleep—overlap can improve throughput.

`multiprocessing` uses separate interpreters (separate GILs) at the cost of pickling data. `asyncio` uses cooperative single-thread multitasking—great for many idle network waits, not for parallel number crunching.

Other Python implementations (Jython, PyPy nuances) differ; production CPython is what most teams ship.

## Code

```python
import threading
import time
from concurrent.futures import ThreadPoolExecutor


def count_forever() -> int:
    total = 0
    for i in range(5_000_000):
        total += i
    return total


def io_wait() -> str:
    time.sleep(0.2)
    return "done"


def run_cpu_threads() -> None:
    start = time.perf_counter()
    threads = [threading.Thread(target=count_forever) for _ in range(4)]
    for t in threads:
        t.start()
    for t in threads:
        t.join()
    elapsed = time.perf_counter() - start
    print(f"CPU threads elapsed: {elapsed:.2f}s")


def run_io_threads() -> None:
    start = time.perf_counter()
    with ThreadPoolExecutor(max_workers=8) as pool:
        list(pool.map(lambda _: io_wait(), range(8)))
    elapsed = time.perf_counter() - start
    print(f"I/O threads elapsed: {elapsed:.2f}s")


if __name__ == "__main__":
    run_cpu_threads()
    run_io_threads()
```

Four CPU threads often take **similar** wall time to one heavy loop. Eight sleeping tasks finish in roughly one sleep window when threaded.

## Common mistakes

- Expecting linear speedup from threads on numeric Python loops.
- Using threads to parallelize CPU work instead of processes or a native library.
- Blaming the GIL for single-threaded I/O code that never used concurrency.
- Sharing mutable globals across threads without locks (GIL does not make dict updates atomic for compound operations).
