Most cheat sheets are organized like a university syllabus: arrays, then linked lists, then trees. Interviews are organized like incidents: a vague story with constraints, and you have minutes to pick a tool. **Pattern-first** teaching closes that gap by naming the invariant before the syntax.

## What “pattern” means here

A pattern is not a memorized template copied from a blog—it is a **repeatable invariant**:

| Pattern | Invariant you protect |
|---------|------------------------|
| Hashing | O(1) lookup of something you already saw |
| Sliding window | Contiguous range stays valid while you expand/shrink |
| Two pointers | Two indices move in a rule that monotonically shrinks search space |
| BFS | Shortest path in unweighted graphs; level-by-level expansion |
| DP 1D | Optimal answer at i built from smaller suffix/prefix |

When a candidate says “I’ll use a hash map” without stating *what* is keyed and *why*, interviewers hear topic-first cramming. When they say “I need last-seen index to move the left bound,” that is pattern-first reasoning—even on a problem they have never seen.

## Topic-first failure mode

Topic-first sounds efficient: finish all tree problems, then graphs. It fails in three predictable ways:

1. **Misclassification** — A problem about consecutive events is not “arrays”; it is sliding window. A problem about prerequisites is not “sorting”; it is graph reachability.
2. **Template overflow** — Candidates paste binary search because the input is sorted, even when the unknown is a feasibility predicate on the answer, not the index.
3. **No exit plan** — They can implement trie insert but cannot articulate when trie beats hash set (prefix queries, compression).

Pattern-first flips the drill: given invariant language, pick structure. Our lesson order in the DSA track interleaves structures only when the pattern demands it—hashing before sliding window because many windows maintain frequency maps.

## How we teach it on StackAtlas

Lessons pair **story → invariant → code → mistakes**. Take [sliding window](/learn/dsa/sliding-window): the body names what the window measures (distinct count, sum threshold) before showing expand/shrink. [Hashing](/learn/dsa/hashing) emphasizes complement and frequency, not “map API trivia.”

Interview questions such as [dsa-longest-substring-no-repeat](/interview/dsa/dsa-longest-substring-no-repeat) grade whether you maintained the uniqueness invariant, not whether you recalled a LeetCode number.

The [DSA cheatsheet](/cheatsheets/dsa) is pattern → clue words → tiny code, not structure → list of 40 problems.

## Study loop that actually sticks

1. Read one pattern lesson.
2. Do one **interview** question cold; speak invariants aloud for two minutes before coding.
3. Open the [DSA visualizer lab](/labs/dsa-visualizer) if the pattern is pointer/window-heavy—watch bounds move.
4. Write a one-line trigger phrase (“longest contiguous with constraint → window + map”).

Spaced repetition beats volume: five patterns understood deeply beat thirty problems where only the solution differed.

## Pattern-first does not mean ignoring foundations

Big-O still matters—you must justify extra space for hashing. [Big-O complexity](/learn/dsa/big-o-complexity) stays the track root so “optimize” is measurable, not vibes.

## Transfer to the job

Production bugs rhyme with interviews: “Why is this consumer slow?” often becomes BFS over retry queues or windowed aggregation over logs—not “tree week.” Pattern vocabulary is how seniors communicate fixes without re-deriving from scratch.

If you are building your own curriculum, sort drills by **invariant**, tag by prerequisite slugs, and resist the urge to label weeks by structure alone. Your future self on a phone screen will thank you.
